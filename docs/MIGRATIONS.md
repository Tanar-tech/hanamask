# DBスキーマ変更とマイグレーションの規約

hanamask は**利用者のPC上のSQLiteファイルが唯一の正**であり、サーバー側に控えが無い。スキーマを変えるということは、**すでに利用者が書き溜めたデータベースをその場で作り替える**ということになる。手順を誤ると、他のどんなバグとも違って**取り返しがつかない**。

対象読者は開発管理者・開発要員。DBのスキーマに手を入れる作業では、着手前に必ず本書を読む。

## 1. なぜ規約が要るのか

2026-08-08 まで、このリポジトリにマイグレーションの仕組みは無かった。`openDb` が起動のたびに `schema.sql` を流すだけで、全テーブルが `CREATE TABLE IF NOT EXISTS` だった。

**この作りは「新規インストールでは正しく、既存の利用者には何も起きない」という形で静かに壊れる。**`schema.sql` に列を足しても、既にテーブルが存在するDBでは `IF NOT EXISTS` によって定義ごと読み飛ばされる。テストは新規DBを作って走るので**全部緑のまま通る**。壊れていることに気付くのは、更新した利用者が自分のデータを開いたときになる。

T36（タスクの本文）で初めてこの問題に当たり、マイグレーション機構（`src/main/db/migrations.ts`）を導入した。

## 2. 絶対に守ること

- **スキーマを変えたら、`schema.sql` と マイグレーション の両方を書く。**片方だけは必ず事故になる。
  - `schema.sql` … **新規**インストールのDBを最新の形で作る
  - `migrations.ts` … **既存**のDBを最新の形へ追いつかせる
- **マイグレーションは冪等にする。**同じDBを何度開いても失敗してはならない。**`apply` 単体が、既に適用済みのDBに対して実行されても失敗しない**ことまで求める（理由は §3.1）。
- **既存の行を消さない・壊さない。**追加した列には既定値を与え、既存行がその値で読めるようにする。
- **`MIGRATIONS` 配列は追記のみ。**既に配布された項目の中身を書き換えたり、順番を入れ替えたりしない。利用者のDBがどの時点の形かは分からない。
- **テストで担保する（詳細は §5）。**「新規DBで動く」テストだけでは、上記の静かな壊れ方を一切検出できない。

## 3. 仕組み

`src/main/db/migrations.ts` は、マイグレーションを配列に列挙して順に適用する。

```ts
interface Migration {
  readonly name: string;
  readonly isApplied: (db: DatabaseHandle) => boolean;
  readonly apply: (db: DatabaseHandle) => void;
}
```

**各マイグレーションが「自分は既に適用済みか」を自分で判定する**（`PRAGMA user_version` のような通し番号は使わない）。理由は `migrations.ts` にコメントとして残してあるとおりで、`schema.sql` が新規DBを最新形で作る以上、通し番号方式だと**番号を2か所で進める必要が生じ、かつ元から必要のないDBにも `ALTER` が走る**ため。

適用の呼び出しは `src/main/db/db.ts` の `applySchema` 直後に置く。**`openDb` を通る経路はすべてここを通る**——これはバックアップ取り込み（`src/main/backup/import-backup.ts`）にとって重要で、取り込みはDBファイルごと差し替えるうえ検証がテーブル名の存在チェックのみのため、**古い形のzipを取り込んでも再オープン時にマイグレーションが追いつかせる**という関係になっている。

### 3.1 同時に2つのプロセスが開いた場合

`isApplied` で確かめてから `apply` するのは check-then-act であり、その隙間に別プロセスが同じ適用を終えていることがある。後発の `ALTER TABLE ... ADD COLUMN` は `duplicate column name` になり、**そのプロセスの起動が丸ごと失敗する**。

このため、

- 列を足すマイグレーションは `addColumnMigration(table, column, definition)` で定義する。`apply` が失敗しても**目的の列が既に存在するなら成功として扱う**（存在しないときだけ送出する）
- アプリ側では `src/main/index.ts` が `app.requestSingleInstanceLock()` で二重起動そのものを抑止し、後発は既存ウィンドウを前に出して終了する（E2Eは `HANAMASK_DB_PATH` で各自のDBを見るため対象外）
- ロック競合の待ち時間（`PRAGMA busy_timeout`）は better-sqlite3 の既定で 5000ms 入っている。`new Database(path, { timeout: 0 })` のように既定を下げない

## 4. SQLiteの制約（設計を縛る）

- `ALTER TABLE ... ADD COLUMN` で **NOT NULL 列を足すときは `DEFAULT` が必須**（既存行に入れる値が無いため）
- 列の**削除・改名・型変更・制約変更は `ALTER TABLE` では基本的にできない**。必要なら「新テーブルを作る → データを移す → 旧テーブルを落とす → 改名する」という手順になる。**これはデータ損失の危険がある作業なので、着手前に管理者の承認を得る**（`docs/GOVERNANCE.md` §6）
- したがって**列の追加は安全、それ以外は要相談**と考えてよい

## 5. テストの要件

以下を満たさないマイグレーションは未完成とみなす。

- [ ] **変更前の形のDBを実際に作り、行を入れてから** `openDb` する。列が追加され、**既存行が消えず、既定値で読める**ことを検証する
- [ ] 同じDBを2回開いても失敗しない（冪等性）
- [ ] **適用済みのDBに対して `apply` を直接呼んでも落ちない**（二重起動時の競合。§3.1）
- [ ] **マイグレーションの呼び出しを外すと、そのテストが実際に落ちる**ことを一度確認する。落ちないなら、それは新規DBだけを見ているテストであり、意味が無い
- [ ] 新規DBでも同じ形になる（`schema.sql` 側の担保）

## 6. リリース前の実データ検証

テストが緑でも、それだけでは配布しない。

1. 利用者（管理者）の実DBを **SQLiteのオンラインバックアップで退避する**。アプリ起動中はWALがあるため、単純なファイルコピーでは整合性が保証されない

   ```bash
   python3 -c "
   import sqlite3
   src = sqlite3.connect('file:<実DBのパス>?mode=ro', uri=True)
   dst = sqlite3.connect('<退避先>.sqlite3')
   src.backup(dst); dst.close()
   "
   ```

2. **その複製に対して本番と同じ `openDb` を通し**、件数が変わらないこと・`PRAGMA integrity_check` が `ok` であることを確認する
3. その上で実インストールを更新し、利用者の目で開けることを確認する

T36 での実績（2026-08-08）: ノート15件・タスク7件・リンク2件・編集履歴1件が保持され、`body` 列が追加、NULL行ゼロ、`integrity_check: ok`。

T42 での実績（2026-08-10）: ノート20件・タスク12件・リンク2件が保持され、`tags` 列が追加、`integrity_check: ok`。

T54 での実績（2026-08-20）: ノート（ページ）32件・タスク14件・リンク2件・編集履歴6件・埋め込み41件が保持され、`notebooks` 表と `notes.notebook_id`・`note_versions.entity_type` が追加。全ページが無所属（`notebook_id` NULL）のまま、既存の版は全件 `entity_type='note'`、包みノートの自動生成なし（notebooks 0件）、`integrity_check: ok`。

T56 での実績（2026-08-20）: `embeddings` の作り直しマイグレーション（CHECK 制約へ 'notebook' 追加）を実DBの複製に適用し、41件が bit 単位で一致（`hex(vector)` 含む全列ダンプの前後比較）、DDL に 'notebook'、`integrity_check: ok`。

## 7. 手順のまとめ

1. `schema.sql` を新しい形に更新する
2. `MIGRATIONS` 配列の**末尾に**項目を追記する（`isApplied` と `apply`）
3. §5 のテストを書く。**マイグレーションを外して落ちることを確認する**
4. `npm test` / `npm run lint` / `npm run typecheck` を通す
5. §6 の実データ検証を行う
6. 本書に実績を追記する
