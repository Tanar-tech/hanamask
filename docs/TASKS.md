# hanamask タスク一覧

`docs/REQUIREMENTS.md`（確定済み要求定義）を実装単位に分解したバックログ。各タスクは概ね1本の `SPEC.md`（skill「feature-spec」）に相当する粒度で、Parallel Subagent Framework（`CLAUDE.md`）のPhase 1〜5フローに1つずつ投入することを想定する。

本ファイルの整備・更新手順は skill「task-breakdown」に従う。要求定義（`docs/REQUIREMENTS.md`）が変更されたとき、または既存タスクの完了・スコープ変更があったときは、このskillを使って本ファイルを更新する。

## 読み方

各タスクは以下5項目を明文化する。

| 項目 | 内容 |
|---|---|
| 目的 | このタスクが無いと何ができないか。`docs/REQUIREMENTS.md`の該当節を根拠として引く。 |
| 変更範囲 | 触ってよい層・ディレクトリの見積もり（ファイル単位の確定はタスク着手時の`SPEC.md` Part 2で行う）。他タスクとの並列実行時に競合しないかの目安。 |
| 禁止事項 | このタスクではやらないこと。スコープ拡張・後続タスクの先取りを防ぐ。 |
| テスト | `docs/TESTING.md`（単体テスト方針）・`.claude/skills/e2e-runner/SKILL.md`（GUI/E2E検証）に基づき、このタスクで最低限満たすべきテスト。 |
| 停止条件 | 管理者に確認せず自律的に進めてよい範囲の境界。`docs/GOVERNANCE.md` §6（管理者承認が必要な操作）に該当する事態、`docs/REQUIREMENTS.md` §8の未決定事項に触れる場合、自己修正3回超過などはここで止める。 |

ステータス: `未着手` / `進行中` / `完了`。

各タスクには「依存」欄を設ける。**必須**は前提タスクが完了するまで着手できないもの（無いと実装・テストが成立しない技術的依存）、**推奨**は無くても着手できるが後回しにした方が手戻りが少ないもの（パターンの横展開・内容の正確性など）を区別する。必須が無いタスクは「必須: なし」と明記する。

### T42: ノート・タスクのタグ付けとグルーピング

- ステータス: 完了（PR #141 / #142 / #143 / #151 / #152）
- 優先度: **高**（管理者要望、2026-08-10）
- 依存: 必須: T36（タスクの本文。タグも同じくタスク側に無かった）／推奨: なし
- 目的: **エージェントが記録を増やし続けると、案件Aの話と案件Bの話が同じ一覧に混ざる。**タグで分けられるようにする。「あるノートがプロジェクトAに所属し、プロジェクトBには所属していない」ことを、利用者が一目で判別できる状態にする。
- **調査済みの現状（2026-08-10）**: タグは**ノートにしか無く、しかも `NoteDetail.tsx` にしか表示されていない**。一覧・検索結果には出ない。**タスクにはタグそのものが無い**（`tasks` テーブルに列が無い）。したがって「一覧を見てどの記録がどの案件か分かる」状態には程遠い。
- **画面案**: モックアップで確認済み（管理者提示済み）。決めた点は以下。
  - **タグは複数持てる**。「プロジェクトA」かつ「設計」は自然に起きるため、1つに絞ると片方を捨てることになる
  - **複数選んだときは OR（どれかに一致）**。「AとBのどちらかを見たい」が主な使い方で、AND は絞り込みすぎて空になりやすい
  - **ノートとタスクを同じ一覧に混ぜる**。案件を横断して探すのは稀なので、種別より案件を優先する
  - **エージェントが付けたタグには印を出す**。人が付けたものと区別が付かないと、誤りを見つけたときに「自分が付けたのか」と迷う
  - **タグの一覧は使われているタグから自動で集める**。先に定義させると、書く前に決めることが増える
- 変更範囲: `src/main/db/`（`tasks` への `tags` 列とマイグレーション、`tasks-repo.ts`）、`src/shared/preload-api.ts`、`src/main/mcp/tools.ts`（`create_task`/`update_task` のタグ、タグでの絞り込み）、`src/main/index.ts`・`src/preload/index.ts`（IPC）、`src/renderer/components/`（一覧へのタグ表示、絞り込み、グループ表示）。
- 禁止事項: タグの正規化・階層化・色の固定割り当てを作り込まないこと（要求に無い）。**タグを先に定義させる画面を作らないこと**（使われているものから集める）。既存のノートのタグの意味を変えないこと。カンバンのカードに絞り込みUIを足さないこと（ドラッグ対象と競合する）。
- テスト: **`tags` 列が無い状態のDBを実際に作ってから** `openDb` し、列が追加され既存行が保持されることのテスト（`docs/MIGRATIONS.md` §5）。`create_task`/`update_task` でのタグの往復。一覧にタグが表示されること。**選んだタグを持たない記録が消えること**（「Aに属しBに属さない」の判別がこれ）。タグが無い記録の扱い。**エージェントが付けた印の有無**が区別できること。
- 停止条件: **エージェントが自動でタグを付ける基準**（どのMCPツールが、何を根拠に付けるか）は画面が固まってから決める。要求定義に無い判断が要るため、着手前に管理者に確認する。既存ノートのタグを一括で書き換える処理は行わない（データの書き換えは不可逆）。

## 定着（作られたものが実際に使われる状態にする）

hanamaskは機能としては動いているが、**開発管理者（このセッション）自身が数日間まったく使わなかった**。タスクは`docs/TASKS.md`、状態は`STATE.md`、実行ログは`loop-run-log.md`に書き続けており、MCPが接続可能な状態でも一度も書き込まなかった。管理者から「hanamaskも使ってね」と言われた後でもそうだった。**「使えること」と「使うこと」の間に段差がある**という観測結果に基づくタスク群。

段差は3層あり、T46（エージェントが書こうと思わない）が最も硬い。T46が無ければT44・T45を整えても書き込みは増えないため、**着手順は T46 → T45 → T44** を推奨する。ただしT44は実装が軽く効果も明確なため、費用対効果では先に来る可能性がある。
