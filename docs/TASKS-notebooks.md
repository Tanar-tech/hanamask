# hanamask ノート/ページ再編タスク（T54〜T59）

`docs/TASKS.md` から分離したタスク一覧。ノート/ページ再編（`docs/REQUIREMENTS.md` §4.9）は統合ブランチ `feature/notebooks` で進めるため、その進捗はこのファイルにだけ書き、`main` 側で並行するパッチ更新が触る `docs/TASKS.md` とは競合させない。書式・「依存」欄の読み方は `docs/TASKS.md` と同じ。統合完了時に `docs/TASKS.md` へ1回だけ転記する。

## 経緯

`docs/REQUIREMENTS.md` §4.9、issue #199。管理者の決定（2026-08-20）: hanamaskは**ノート**（ページをとりまとめる束。概要を持つ）と**ページ**（旧「ノート」＝記録の基本単位）の2概念を持ち、両者は**並列の存在**（リンク・タグ・意味検索の索引・編集履歴・ゴミ箱はどちらにも付きうる）。**無所属ページを許し**、既存データは**全て無所属ページに移行**する（IDは維持、包みノートは作らない）。MCP互換は**案A**（既存 `*_note` 系ツールは名前・引数・戻り値を変えずページ操作として温存し、`*_page` / `*_notebook` を新設。旧名の廃止はv3まで行わない）ため、本改定は**v2.1.0（マイナー）**。

**ブランチ運用（2026-08-20、管理者指示）**: v2.0.0（ローカルLLM）と同方式で、統合ブランチ **`feature/notebooks`**（`main`から分岐）を置く。T54〜T59の各PRは`main`ではなく`feature/notebooks`をbaseにする。`main`に入ったパッチ更新は、`main`→`feature/notebooks`のマージPRで随時取り込む（rebaseはしない）。全タスクが揃った時点で`feature/notebooks`→`main`のPRを1本出し、そこでマイナーバージョンを上げる。要求定義（§4.9）の改定と`docs/TASKS.md`からの参照だけは先に`main`へ入れ、`docs/TASKS.md`本体にはそれ以降触れない。

### T56: ノート/ページ(3) 意味検索の索引をノートへ広げる

- ステータス: 完了（PR #207、`SPEC.md`。§6実データ検証41件bit一致）
- 優先度: 中
- 依存: 必須: T54, T55（`EntityType` の拡張が前提）／推奨: なし

- 変更範囲: `src/main/db/migrations.ts`・`schema.sql`（`embeddings` の作り直し）、`src/main/db/embeddings-repo.ts`（UNION SQL 3箇所）、`src/main/llm/indexer`（subscribe の追加）、`src/shared/`（`SemanticSearchResult`）、`src/main/mcp/tools.ts`（`semantic_search_notes` の戻り値）、`src/renderer/components/`（関連ノート欄・検索結果の表示）。

- 依存: 必須: T57／推奨: T56, T58（生成した概要が検索・画面に出て初めて効果が見える）
- 目的: `docs/REQUIREMENTS.md` §4.9。ノートの概要（何の案件か・どこまで進んだか）を所属ページの内容から**自動生成し、ページの追加・更新に合わせて追従更新する**。手で書かなくてもノートが読める入口になっている状態を作る。
- **§4.8-3（提案系補助）との関係**: 「提案→利用者が採用」の原則に対する**限定的な例外**として、対象がノートの概要に限られる（ページ本文＝利用者の記録そのものは書き換えない）ことを前提に、自動更新を認める。この境界を広げない。
- 変更範囲: 生成主体の決定（停止条件）により変わる。外部AIエージェントに任せる場合は `src/main/mcp/tools.ts`（ツールの説明文・案内）と運用ドキュメントのみ。同梱ローカルLLMで行う場合は `src/main/llm/`（生成プロンプトと構造化出力）、`src/main/notify/`（更新をトリガーにした再生成）、`src/renderer/components/`（自動生成であることの表示・手動編集との切り替え）。
- 禁止事項: **利用者が手で書いた概要を、断りなく上書きしないこと**（手動編集の有無を持ち、上書きしないか確認を挟む）。ページ本文・タイトル・タグを自動で書き換えないこと（例外は概要のみ）。ページの更新のたびに無条件で推論を走らせて、アプリを重くしないこと（間引き・遅延を設計する）。概要の生成のために記録の内容を外部へ送らないこと（ローカルLLMで行う場合）。生成に失敗したときにノートの保存や他の機能を止めないこと。ログに本文を出さないこと。
- テスト: 推論層をモックし、概要が生成・更新される流れ。**手動編集された概要が上書きされないこと**。生成が失敗・未準備のときにノートが従来どおり使えること。ページの追加・更新・移動・削除それぞれで追従更新のトリガーが正しく引かれること（および間引きが効くこと）。採用前後でDBがどう変わるか（自動更新を認める範囲を超えていないこと）。
- 停止条件: **生成主体を管理者に確認してから着手する**（§8）。(a) 外部AIエージェントに任せる（ツールの説明文で促すだけ。追加の依存なし）か、(b) 同梱のローカルLLMで行う（**T50「提案系補助」の前倒しが必要**。チャット用の生成モデルが要るためT49にも波及する）か。トリガー（ページ更新の都度か、明示的な指示のときだけか）も併せて確認する。自動更新の対象を概要以外へ広げる判断は管理者に確認する。
