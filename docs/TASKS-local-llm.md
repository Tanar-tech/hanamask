### T48: ローカルLLM(1) 意味検索（埋め込み）

- ステータス: 完了（PR #195、`SPEC.md`。2026-08-20 に Windows 実機確認済み、v2.0.0 として main へ統合）
- 優先度: **高**（管理者決定、2026-08-19）
- 依存: 必須: なし／推奨: T46（記録が増えてからでないと意味検索の効果が見えない）
- 目的: `docs/REQUIREMENTS.md` §4.8-1。ノート・タスク本文を同梱の埋め込みモデルでベクトル化してSQLiteに保存し、意味的に近い記録を探せるようにする。MCPツール `semantic_search_notes` として公開し、外部AIエージェントが「作業前に過去の経緯を引く」精度を上げる（キーワードが一致しない記録も引ける）。UIでは詳細画面の「関連ノート」欄と検索結果への併記。**ランタイム同梱（`node-llama-cpp`＋electron-builderの`asarUnpack`）とモデル同梱の配布経路をここで固める**のが、後続T49/T50の基盤になる。
- 変更範囲: `package.json`（`node-llama-cpp` 追加、`build` の `asarUnpack`/`extraResources`）、`src/main/llm/`（新設: ランタイムの読み込み、埋め込みの計算、推論層のインターフェース）、`src/main/db/`（埋め込み保存用テーブルとマイグレーション。`docs/MIGRATIONS.md` を読んでから）、`src/main/mcp/tools.ts`（`semantic_search_notes`）、`src/main/notify/`（更新通知に乗せた再インデックス）、`src/renderer/components/`（関連ノート欄）、`README.md`（ツール一覧）、`docs/PACKAGING.md`。
- 禁止事項: sqlite-vec等のネイティブ拡張を追加しないこと（個人規模なのでJS側のコサイン類似度総当たりで足りる。ネイティブ依存は`node-llama-cpp`の1つに留める）。既存の`search_notes`の挙動を変えないこと。記録の内容を外部へ送らないこと。モデルが未準備・読み込み失敗のときにアプリ全体やMCPサーバーを止めないこと（意味検索だけが「未準備」を返す）。
- テスト: 推論層をインターフェースで隔離し、単体テストは固定ベクトルを返すモックで通す（CIで実モデルを走らせない）。埋め込みテーブルのマイグレーション（既存DBに列・表が足され既存行が保持されること）。ノート更新後に埋め込みが再計算されること・削除済みノートが結果に出ないこと。モデル未準備のときの`semantic_search_notes`の応答。同梱の小モデルで実際に1件だけ推論するE2E（Windows実機で。CIでは任意）。
- 実績（2026-08-19、セット0の検証）: **cl-nagoya/ruri-v3-70m（Apache-2.0）を採用**。自前変換 GGUF Q8_0（73.4MiB）で HF sentence-transformers との一致 cos min 0.99986。公開GGUFは濁点が消える不良品のため使わず、自前変換版を GitHub Release アセット `embedding-model-ruri-v3-70m-q8_0-v1` で配布（sha256 `5d1c83a9…`、管理者がアップロード）。必須対処: BOS をトークン配列で明示、`batchSize = contextSize`（2048）、プロバイダ側でトークン数切り詰め。詳細は `docs/local-llm/embedding-model-verification.md`、変換パッチと検証スクリプトは `scripts/embedding-model/`。
- 停止条件: **同梱する埋め込みモデルの選定**（**再配布可能なOSSライセンスであること・日本語主体で品質を確かめること**が条件（§4.8）。サイズは~100〜200MBのGGUFを目安に候補を挙げる）と、それによるインストーラーサイズの増分は、着手前に管理者へ提示して確認する。`node-llama-cpp`の追加は`docs/GOVERNANCE.md` §6の依存関係追加に該当（2026-08-19に方針として承認済み。バージョン・プリビルドの構成を確認してから入れる）。ベクトルをDBに持つかファイルに持つかで迷ったらSPECで管理者に確認する。

### T49: ローカルLLM(2) チャットのローカルモデル

- ステータス: **ドロップ（2026-08-27、管理者判断）**。§4.11（双方向コミュニケーション、T62）を優先する。モデル候補・ライセンス・配布2系統の調査結果は PR #225 のブランチ（`feat/t49-local-chat` の SPEC.md）に保存済みで、再開時に再利用する
- 優先度: 中
- 依存: 必須: T48（ランタイム同梱・モデル取得の経路）, T12（既存のチャットとエージェントループ）／推奨: なし
- 目的: `docs/REQUIREMENTS.md` §4.8-2。設定画面からチャット用モデルを取得（userDataへダウンロード・進捗表示・削除）し、チャットのプロバイダをAnthropic APIとローカルモデルで切り替えられるようにする。ローカルモデルもtool useで§7のMCPツール群を呼び、`ChatModelClient`（`src/main/chat/agent-loop.ts`）の実装を1つ足す形で既存ループを共用する。tool useに対応しないモデルではツールなしチャットに劣化させ、UIで明示する。応答のストリーミングも併せて入れる（ローカルモデルは遅く、全文待ちだと止まって見えるため）。
- 変更範囲: `src/main/llm/`（チャット推論、モデルの取得と管理）、`src/main/chat/`（ローカル用`ChatModelClient`実装、プロバイダ切替）、`src/main/settings/chat-settings.ts`（プロバイダ・モデルパス）、`src/renderer/components/`（設定画面のモデル管理、チャットのストリーミング表示）、`src/shared/preload-api.ts`・IPC。
- セキュリティ（管理者指示 2026-08-19、SPECで具体化する）: ノート本文は外部エージェントが書く**信頼できない入力**であり、小型ローカルモデルはクラウドモデルよりプロンプトインジェクションに弱い。**ローカルモデルには書き込み系MCPツールを渡さない／許可リストで絞る**選択肢をSPECで検討する。既存ガードレール（`confirm: true` 必須・ソフトデリート＋30日復元）は崩さない。**利用者が自分で用意したGGUFを置く経路**を許すかは慎重に決め、許すなら「信頼できるファイルだけ」を明示し、取得経路はHTTPS固定URL＋sha256検証に限る。モデル取得以外で外部通信を発生させない。
- 禁止事項: Anthropic API経路を壊さないこと（BYO Agentは残す）。モデルのダウンロード元をハードコードした1URLに依存させ、失敗時にアプリが起動しなくならないこと。利用者の同意なくモデルの自動取得を始めないこと（大容量）。T12が凍結中（画面から外している）である前提を、管理者の判断なく解除しないこと。
- テスト: プロバイダ切替のテスト（モックの`ChatModelClient`で両経路が同じループを通ること）。tool use非対応モデルのときの劣化挙動。ダウンロードの中断・再開・失敗時の状態。ストリーミングのイベント順序。
- 停止条件: 取得できるチャットモデルの候補一覧（サイズ・ライセンス・日本語品質・tool use対応。**再配布可能なOSSライセンスと日本語主体の評価**が条件、§4.8）を管理者に提示して確認してから実装する。T12凍結の解除（チャットを画面に戻す）は管理者判断。

### T50: ローカルLLM(3) 提案系補助

- ステータス: 未着手（SPEC未作成。issue #181）
- 優先度: 低
- 依存: 必須: T48／推奨: T49（チャット用モデルを流用するため。埋め込みモデルだけでは生成ができない）
- 目的: `docs/REQUIREMENTS.md` §4.8-3。タグ・タイトルの提案、長文ノートの要約、本文からのタスク候補の抽出を、ローカルモデルで行う。**必ず「提案→利用者が採用」の形**にし、モデルが記録を勝手に書き換えない。
- 変更範囲: `src/main/llm/`（提案用のプロンプトと構造化出力）、`src/renderer/components/`（詳細画面・編集画面の提案UI）、`src/shared/preload-api.ts`・IPC。
- セキュリティ（管理者指示 2026-08-19）: 提案の生成元テキストは信頼できない入力なので、提案は必ず利用者が採用する形を守る（インジェクションで記録が書き換わらない）。ログに本文を出さない。
- 禁止事項: 提案の自動適用。MCPツールとして外部エージェントに提案機能を公開しないこと（外部エージェントは自分で考えられる）。提案のためにノート本文を外部へ送らないこと。
- テスト: 推論層をモックし、提案の表示・採用・却下の流れ。採用しない限りDBが変わらないこと。モデル未取得のときにUIが「未準備」を示し、他の機能に影響しないこと。
- 停止条件: 提案の種類（何を提案するか）を増やす判断は管理者に確認する。提案UIの配置は画面案を提示してから決める。
