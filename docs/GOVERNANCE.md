# hanamask リポジトリ管理規約

本規約は hanamask（ローカルElectronデスクトップアプリ、詳細は [docs/REQUIREMENTS.md](REQUIREMENTS.md)）開発における体制・役割・作業ルールを定める。

> 2026-08-03: アーキテクチャをNext.js/PostgreSQL/AWSサーバーレス構成からElectron+MCPサーバー+SQLiteのローカル完結型デスクトップアプリへ全面転換（docs/REQUIREMENTS.md確定）。本規約中、旧構成に依存していた記載（§3.1 PRプレビュー環境、§8のマルチテナント認可ルール等）は本改訂で削除・更新した。

## 1. 目的

- 管理者・開発管理者・開発要員（サブエージェント）が異なる粒度で並行して作業することを前提に、
  権限の所在と作業の入出力ルールを明確にし、意図しない破壊的変更や品質低下を防ぐ。
- 本規約は開発の進行に伴って改訂される。改訂ルールは [11. 規約自体の改訂](#11-規約自体の改訂) を参照。

## 2. 体制と役割

| 役割 | 担当 | 責務 |
|---|---|---|
| 管理者 | ユーザー本人 | 要件定義、優先順位決定、リリース可否・破壊的操作の最終承認 |
| 開発管理者 | このチャット（Claude Code、通常Fableモデル） | タスク分解、開発要員への指示、成果物レビュー、ブランチ/PR管理、品質保証、進捗報告 |
| 開発要員 | 主に OpenAI Codex CLI（herdr経由でworktreeごとに並列起動）。小規模タスクは会話内Agent toolやCursorサブエージェントも利用可 | 個別タスクの実装・テスト・調査、開発管理者への報告 |

- 開発管理者は管理者の代理として意思決定を行わない。[6. 管理者の承認が必要な操作](#6-管理者の承認が必要な操作)に該当する事項は、必ず事前に管理者へ確認する。
- 開発要員は開発管理者からの委任範囲内でのみ作業する。委任範囲外の判断が必要になった場合は作業を中断し、開発管理者に差し戻す。
- 並列実行は [herdr](https://herdr.dev)（複数AIエージェントセッションをターミナル上で並行管理するツール。VSCodeの統合ターミナル内で動作する）を主手段とする。開発管理者（Claude Code）がherdr上で各セッションを統括し、実装は主にCodexセッションが担う。セットアップ・運用方法は [docs/HERDR.md](HERDR.md)・[docs/CODEX.md](CODEX.md) を参照。

## 3. ブランチ戦略

- `main`: 保護ブランチ。常にビルド可能・動作する状態を維持する。直接コミットは行わない。
- 作業ブランチは用途別プレフィックスを付ける。
  - `feature/xxx`: 新機能
  - `fix/xxx`: バグ修正
  - `chore/xxx`: 雑務・設定変更
  - `refactor/xxx`: リファクタリング
- 開発要員にタスクを委任する際は、原則として独立した worktree で作業させ、`main` を含む他ブランチに影響を与えないようにする。
  - 並列実行するタスクは、タスクごとに `git worktree` を作成し、herdr でそれぞれ独立したCodex CLIセッションとして起動する（[docs/HERDR.md](HERDR.md)・[docs/CODEX.md](CODEX.md) 参照）。
  - 単一の会話内で完結する小規模なタスクは、従来どおり Agent tool の `isolation: "worktree"` や Cursorサブエージェント（`.cursor/agents/`）を用いてもよい。
- 作業ブランチから `main` へのマージは、開発管理者によるレビュー完了後に行う。マージ方法（マージコミット/squash等）は当面 squash merge を基本とし、履歴を単純に保つ。

### 3.1 デプロイ・配布（2026-08-03改訂）

hanamaskはローカル完結のElectronデスクトップアプリであり、AWSサーバーレス構成・PRプレビュー環境は廃止した。配布はインストーラー（`electron-builder`等）の再配布によるため、クラウド上のデプロイパイプラインは不要（docs/REQUIREMENTS.md §5）。

## 4. コミットルール

コミットメッセージの基本形式（Conventional Commits）・粒度・Git操作の可否は `~/.claude/CLAUDE.md`（グローバル規約）の Git Operations 節に従う。本プロジェクト固有の差分のみ以下に記す。

- プレフィックスはグローバル規約の `feat:`/`fix:`/`refactor:`/`docs:`/`chore:` に加え、テスト専用コミットには `test:` も使用してよい。
- コミットメッセージの言語は日本語・英語どちらでも可（1コミット内で混在させない）。
- PRマージ方式（squash merge）・日常的なGit操作（commit/push/PR作成）の自律実行は、2026-07-29の管理者判断によりグローバル規約側を本プロジェクトの運用に合わせて更新済みのため、両者は一致している（[11.1](#111-グローバル規約との重複整理2026-07-29対応) 参照）。

## 5. レビュー運用

- 開発要員が作成したコード・成果物は、`main` へ反映する前に必ず開発管理者がレビューする。
  - 差分の意図を理解しているか（レビューの丸投げをしない）
  - 過剰な実装・不要な抽象化がないか
  - セキュリティ上の懸念（OWASP Top 10等）がないか
  - 既存のコーディング規約・アーキテクチャとの整合性
- 差分を読む手段は hunk（ターミナル差分ビューア）を主とする。指摘を差分行の真横にインラインコメントとして置けるため、指摘とコードの対応が保たれる。導入・使い方は [docs/HUNK.md](HUNK.md) を参照。ただし hunk のコメントはセッション終了で消えるため、確定した指摘はPRコメントに転記する。
- 動作確認が可能な変更（UI変更・実行可能なロジック）は、レビュー時に実際に動作させて確認する（`/verify` 相当のプロセス）。テストが通ることと機能が正しいことは別であることに留意する。
- レビューで問題が見つかった場合は開発要員（サブエージェント）に差し戻す。開発管理者が直接修正するのは軽微な修正に留める。

## 6. 管理者の承認が必要な操作

以下は開発管理者が単独で実行せず、事前に管理者へ確認・承認を得る。

- `main` ブランチへの破壊的操作（force push, `reset --hard`, ブランチ削除）
- リリース・タグ付け、公開リポジトリへの push
- 依存関係の大幅な追加・削除・メジャーバージョンアップ
- CI/CD・ビルドパイプラインの設定変更
- アーキテクチャ上の不可逆な決定（採用フレームワーク、DB選定、配布方式など）
- 外部サービス・APIキー・シークレットに関わる設定
- 本規約自体の改訂

上記に該当しない日常的な開発作業（ブランチ作成、実装、テスト、ドキュメント更新、`main` への通常マージ）は開発管理者の裁量で進めてよい。

## 7. 開発要員（サブエージェント）運用ルール

- タスクは独立して検証可能な単位に分解してから委任する。委任時には目的・背景・完了条件を明示する（詳細はAgent運用の指針に準ずる）。
- サブエージェントの成果は「実施したと申告した内容」ではなく、実際の差分・出力を開発管理者が確認してから採用する。
- 複数のサブエージェントに並行してタスクを委任する場合、担当領域（ファイル・機能範囲）が重複・競合しないよう開発管理者が事前にタスクとworktreeを分割する。
- 機密情報（APIキー、個人情報、認証情報）をタスク指示やコード中に含めない。

### 7.1 herdr を用いた並列実行フロー

開発管理者（Claude Code）が統括役、Codex CLIセッションが実装役という分担を基本とする。

1. 開発管理者がタスクを独立した単位に分解し、タスクごとに `git worktree add` で作業ツリーを作成する。
2. `herdr agent start <task-name> --cwd <worktree-path> -- codex` で各worktreeに対応するCodex CLIセッションを起動する（詳細は [docs/CODEX.md](CODEX.md)）。Claude Code CLIセッションを直接使いたい場合は `-- claude` でも起動できる。
3. herdrのダッシュボードで各セッションの状態（idle/working/blocked）を監視し、対応が必要なセッションを把握する。
4. セッションが完了（idle）になったら、開発管理者が差分を確認する（[5. レビュー運用](#5-レビュー運用)に従う）。対象worktreeで `hunk diff --watch` を開いてレビューし、指摘はインラインコメントとして差分行に置く（[docs/HUNK.md](HUNK.md)）。Codexの成果物も、開発要員（サブエージェント）の成果物と同様に扱い、申告内容を鵜呑みにしない。
5. レビュー完了後、作業ブランチをPR経由で `main` にマージし、対応するworktreeを削除する。
6. herdr・Codex自体の設定（`~/.claude/settings.json`・`~/.codex/config.toml` 等へのフック追加等）を変更する操作は、[6. 管理者の承認が必要な操作](#6-管理者の承認が必要な操作)には該当しないが、各ツールの権限・監督面に関わるため、変更前に管理者へ確認する。

### 7.2 Parallel Subagent Framework（1機能内の並列実行フロー）

herdr（7.1）が複数の独立したタスクをworktree単位で並列化する仕組みであるのに対し、こちらは**1つの機能の実装**を、単一のClaude Codeセッション内でフェーズ単位・サブエージェント単位に並列化する仕組みである。Docker・追加worktreeを必要とせず、開発管理者のセッション内で完結する。両者は併用可能（例: herdrで複数機能を並行させつつ、各worktree内で本フローを使う）。

骨格・フェーズ定義・呼び出すスキル・停止ポイントの詳細は [CLAUDE.md](../CLAUDE.md) の「Parallel Subagent Framework」節を正とする（本規約とCLAUDE.mdの記載が食い違った場合はCLAUDE.mdを都度更新し一致させる）。要点のみ以下に記す。

1. Phase 1（調査・並列・読取専用）→ Phase 2（仕様書生成、skill「feature-spec」）→ **停止①: 仕様書Part 1を管理者がレビュー・承認** → Phase 3（実装・並列・TDD、`.claude/agents/implementer.md`）→ Phase 4（統合ゲート・逐次）→ Phase 5（検証・並列、`.claude/agents/reviewer.md`）→ **停止②: `/structured-review`（skill「structured-review」）で管理者が起動する構造化レビュー**。
2. 停止①・停止②以外では確認を挟まず自律的に進める。ただし [6. 管理者の承認が必要な操作](#6-管理者の承認が必要な操作)に該当する事態が判明した場合はその場で止まり管理者に確認する（本節の「自律的に進める」より優先する）。
3. Phase 3の並列実装は、Phase 2で宣言した「並列グループ」（ファイルが重複しないセット）単位でのみ行う。共有ファイルの編集はPhase 4に限定する。
4. テストの削除・無効化やアサーションを緩めることで「グリーンにする」ことは、開発管理者・開発要員のいずれであっても禁止する（[5. レビュー運用](#5-レビュー運用)の趣旨を機械的なごまかしから守るための明文化）。
5. フロー起動時は完了条件と上限ターン数を明示し、無条件に自走させない（セーフティ機構の詳細はCLAUDE.md参照）。

## 8. コーディング規約

一般的なコーディングスタイル・コメント方針（YAGNI、コメントは「なぜ」のみ等）は `~/.claude/CLAUDE.md`（グローバル規約）の Coding Style / Comments 節に従う。本プロジェクト固有の規約のみ以下に記す。

- 技術スタック（2026-08-03改訂。旧: Next.js/PostgreSQL/AWSサーバーレス構成）: Electron（デスクトップアプリ本体）+ Node.js製MCP SDK（mainプロセス内蔵のMCPサーバー）+ SQLite（ローカルDB）。UI（レンダラープロセス）の詳細実装は基盤実装時に確定する。詳細は [docs/REQUIREMENTS.md](REQUIREMENTS.md) 参照。
- テスト: 単体テストは Vitest（既存採用ランナー、グローバル規約の「既存ランナーがあれば従う」に該当）。テストケース作成方針（ディレクトリ構成、I/O境界の扱い等）は [docs/TESTING.md](TESTING.md) を参照。
- Anthropic APIキー等の秘密情報はElectronの `safeStorage`（OSセキュアストレージ）で暗号化して保存する。環境変数(.env)やサードパーティの汎用キーストアは使わない（docs/REQUIREMENTS.md §4.6）。

## 9. セキュリティ・シークレット管理

- APIキー・パスワード等の秘密情報はリポジトリにコミットしない。`.gitignore` に環境変数ファイル等を追加する。
- 誤って機密情報を含むファイルをステージした場合、コミット前に必ず内容を確認する。
- 脆弱性（インジェクション、XSS等）につながる実装に気づいた場合は直ちに修正する。

## 10. ドキュメント管理

- `README.md`: プロジェクト概要、セットアップ手順（利用者・開発者向け）

- `CLAUDE.md`: Claude Code セッション向けのプロジェクト固有指示（本規約の要点を参照する形で維持）
- `docs/HERDR.md`: herdrによる並列サブエージェント運用のセットアップ・使い方
- `docs/CODEX.md`: OpenAI Codex CLIのセットアップ・herdr連携・開発要員としての運用方法
- `docs/TESTING.md`: テストケース作成方針（ディレクトリ構成、I/O境界の扱い等）
- `docs/PACKAGING.md`: Windows向けインストーラーのビルド手順・`electron-builder`設定の意図・スコープ外事項（[3.1](#31-デプロイ配布2026-08-03改訂) の配布方針の具体手順）
- `docs/AUTO_UPDATE.md`: 自動更新（`electron-updater`）の調査結果。**未実装**。リポジトリ公開の判断とセットになる
- `docs/MIGRATIONS.md`: DBスキーマ変更とマイグレーションの規約。**スキーマに手を入れる作業では着手前に必読**（既存利用者のデータを壊さないための手順・テスト要件・実データ検証）
- `docs/TASKS.md`: `docs/REQUIREMENTS.md`を実装単位に分解したタスク一覧（目的・変更範囲・禁止事項・テスト・停止条件）。整備・更新手順は skill「task-breakdown」を参照。
- `.claude/agents/`: Claude Codeサブエージェント定義（`implementer`/`reviewer`/`verifier`）。7.2のフローで使用する。
- `.claude/skills/`: Claude Codeスキル定義（`feature-spec`/`structured-review`/`e2e-runner`）。7.2のフローで使用する。
- 変更履歴が必要になった場合は `CHANGELOG.md` を別途導入する。

## 11. 規約自体の改訂

- 本規約の変更は管理者の承認を得て行う。
- 改訂時はコミットメッセージに変更理由（Why）を明記する。

### 11.1 グローバル規約との重複整理（2026-07-29対応）

`~/.claude/CLAUDE.md`・`~/.claude/skills/`・`~/.claude/docs/` にグローバル規約一式が整備されたことを受け、本ファイルおよび [CLAUDE.md](../CLAUDE.md) からグローバル規約と純粋に重複する記載（Conventional Commitsの基本形式、コメント方針、YAGNI等の一般的コーディングスタイル）を削除し、プロジェクト固有の内容（体制・herdr/Codex運用・Parallel Subagent Framework・マルチテナント認可ルール等）のみを残す整理を実施した。矛盾する場合は本ファイル側を優先する運用（グローバル規約冒頭の取り決め通り）は維持している。

整理の過程で、グローバル規約とのアーキテクチャ上の相違点が2件見つかった（PRマージ方式＝merge commit必須/squash禁止 vs 本規約のsquash merge基本、Git操作の確認要否＝都度確認必須 vs 本プロジェクトの自律実行）。管理者に確認したところ、本プロジェクトの運用（squash merge・commit/push等の自律実行）に合わせてグローバル規約側を更新する判断となり、2026-07-29付けで `~/.claude/CLAUDE.md` を改訂済み。したがって現在は両者に相違はない。

### 11.2 テスト規約の適合確認（2026-07-30対応）

`~/.claude/docs/testing.md`（グローバル規約）と本プロジェクトのテスト実装を突き合わせ、以下を確認した。

- **テストランナー**: グローバル規約は `node:test` をデフォルトとしつつ「既存プロジェクトが別ランナー（例: Vitest）を使っていればそれに従う」としており、本プロジェクトは元々Vitestを採用済みのため準拠（docs/GOVERNANCE.md §8）。
- **既知の相違（意図的・許容）**: グローバル規約はテストを `test/` ディレクトリ・`test_xxx.ts` 命名で置くことをMUSTとしているが、本プロジェクトは `tests/` ディレクトリ・Vitest標準の `*.test.ts` 命名を採用済み（10ファイル以上の既存資産があり、Vitestの規定動作・`vitest.config.ts` の `include` 設定とも整合するため）。移行コストに見合わないと判断し、現状維持とする。矛盾時は本ファイル側を優先する運用（§11.1）に従う。
- **カバレッジの不足を発見・解消**: `src/server/handlers/` のハンドラ層に複数の欠落があった。
  - `auth.ts`（register/login/logout/session/requestPasswordReset/resetPassword）: テストが一切無かった。特にパスワードリセット機能はメール列挙攻撃対策（存在有無で応答を変えない）を含め無テストだったため、`tests/auth.test.ts`（30ケース）を新規追加。
  - `projects.ts`: `createProject` のみテスト済みで `listProjects`（`?all=1` を含む）・`updateProject`・`deleteProject` が未テストだったため `tests/projects.test.ts` に追加。
  - `stats.ts`: `getStatsSummary` のみテスト済みで `exportStatsSummary`（CSVエクスポート）が未テストだったため `tests/stats.test.ts` に追加（CSVエスケープ・BOM付与等を含む）。
  - `tasks.ts`: ハンドラ層（`getOpenTask`/`postTaskAction`/`getTasksInRange`/`patchTask`/`deleteTask`）が丸ごと無テストだった（内部の `task-timer.ts`/`task-patch.ts` は別途テスト済み）。`tests/tasks-handlers.test.ts` を新規追加。
  - 追加したテストは全て、対応するコードを一時的に壊して赤くなることを確認済み（`~/.claude/docs/testing.md` の「新しいテストは対象コードが壊れたら失敗することを確認する」に従う）。
- 対応後、`npm test`（181テスト）・`npm run lint`・`tsc --noEmit`・`npm run build` は全て成功。
