# work-manager 要求定義書

## 0. 改訂メモ（Webアプリ化）

本書は当初 Windows デスクトップアプリ（.NET/WPF・WinUI3）として書かれていたが、商品として販売する方針に伴い **Webアプリケーション（SaaS）** へ方針転換した。タスク管理・工数管理の中核要求（§1〜§4、§6の基本部分）は変更しない。変更点は主に非機能要件（§5：技術スタック・データ保存・配布形式）と、商用化に伴う新規要件（§4.6〜§4.9、§9）である。

## 1. 概要

### コンセプト
タスク管理と工数管理を一体化し、最小労力の入力フォームを提供するWebアプリケーション。個人利用に加え、チーム・組織単位でも契約・利用できる商用SaaSとして提供する。

### 想定ユーザー
- 個人ユーザー: ブラウザから利用する開発者・知識労働者。
- チーム/組織ユーザー: 組織管理者が契約し、メンバーを招待して利用する。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| プロジェクト/カテゴリ | タスクが属する分類。事前にマスタ登録し、タスク入力時に必須選択する。組織（テナント）ごとに独立する。 |
| タスク | 「プロジェクト/カテゴリ」＋「タスク名（自由入力）」で構成される作業単位。開始時刻・終了時刻を持つ。 |
| 休憩 | タスクと同様に開始・終了を記録する特別な作業単位。工数集計上は通常タスクと区別する。 |
| 終業 | その日の作業をすべて終了する操作。実行中のタスク/休憩をクローズし、当日の記録を確定する。 |
| 組織（テナント） | 契約の単位。1人以上のユーザーが所属し、プロジェクト/カテゴリ・タスクデータを共有する。個人利用は「メンバー1名の組織」として扱う。 |
| プラン | 組織に紐づく契約プラン（Free / Pro 等）。利用できる機能・メンバー数上限を決める。 |

## 3. 利用シーン・フロー

1. **サインアップ / ログイン**: メールアドレス（+パスワードまたはメールリンク）でアカウント作成し、ブラウザからアプリにアクセスする。
2. **組織作成 or 招待承諾**: 初回ログイン時に新規組織を作成する、または既存組織からの招待を承諾して参加する。
3. **タスク開始**: 利用者が「プロジェクト/カテゴリ」を選択し、「タスク名」を入力して開始する。
4. **タスク切替**: 実行中のタスクの終了時刻を記録すると同時に、次のタスク（プロジェクト/カテゴリ＋タスク名）を入力して開始する（前タスクの終了時刻＝次タスクの開始時刻）。
5. **休憩**: 「休憩」を特別なタスクとして明示的に開始・終了する。休憩明けは通常のタスク開始と同様の操作で再開する。
6. **終業**: 「タスク完了」操作により、その日最後の実行中タスク（または休憩）を終了し、当日の作業記録を確定する。
7. **タスク一覧化**: 任意のタイミングで、設定した期間（週単位・月単位など）のタスク実行状況をカレンダー形式で確認する。
   - 週単位表示: 各日のタイムラインに沿って表示（Outlookカレンダーのような形式）。
   - 月単位表示: 各日で実行したタスクを数値単位（件数・時間など）で表示。
8. **（組織管理者）メンバー招待・プラン管理**: 組織管理者はメンバーを招待し、契約プラン・支払い方法を管理する。

## 4. 機能要件

### 4.1 タスク実行管理
- ブラウザ上でどこからでもアクセス可能（PWA化してホーム画面追加・オフライン時の閲覧に対応することを検討、初期スコープは要確認 → §7）。
- プロジェクト/カテゴリの選択（必須、事前登録済みマスタから選択。運用中の新規作成可否は [7. 未決定事項](#7-未決定事項今後確認したい項目) を参照）。
- タスク名の自由入力。
- タスク開始・終了時刻の自動記録（前タスク終了＝次タスク開始、サーバー側のUTC時刻を正とし、表示はユーザーのタイムゾーンに変換する）。
- 休憩の開始・終了(通常タスクと区別して記録)。
- 終業操作(当日の作業記録を確定)。
- 実行中タスクの常時表示(現在何を実行中かが一目でわかる。ブラウザタブタイトル/favicon等での表示も検討)。

### 4.2 マスタ管理
- プロジェクト/カテゴリの登録・編集・削除（アーカイブ）。組織単位で管理し、組織内メンバーで共有する。

### 4.3 タスク一覧化・カレンダー表示
- 表示期間の設定（週単位・月単位を基本とする。日単位等の要否は要確認）。
- 週表示: タイムライン形式（時間軸に沿ってタスクをブロック表示）。
- 月表示: 日ごとのタスク実行状況を数値で表示（集計単位は要確認）。
- プロジェクト/カテゴリ別の視覚的な区別（色分け等）。

### 4.4 データ編集・修正
- 過去の記録（開始/終了時刻、タスク名、プロジェクト/カテゴリ）の修正。
- タスク記録の削除。

### 4.5 工数集計
- プロジェクト/カテゴリ別・日別・週別・月別の工数（時間）集計。
- 集計結果の外部出力（CSV/Excel等）の要否は要確認。

### 4.6 アカウント・認証（商用化に伴う新規要件）
- メールアドレスによるサインアップ・ログイン（パスワード認証を基本とし、将来的にOAuth（Google等）を追加検討）。
- パスワードリセット。
- セッション管理・ログアウト。

### 4.7 組織（マルチテナント）管理（商用化に伴う新規要件）
- 組織の作成・組織名/ロゴ等の基本設定。
- メンバー招待（メールリンク）・ロール管理（管理者/一般メンバー、最低限の2階層）。
- メンバー削除・組織からの離脱。
- 組織単位でのデータ分離（他組織のプロジェクト/カテゴリ・タスクは参照不可）。

### 4.8 プラン・課金管理（商用化に伴う新規要件）
- プラン一覧・料金表の提示（マーケティングページ）。
- Free / Pro 等の複数プランを用意し、プランごとにメンバー数上限・機能制限（例: エクスポート機能はPro限定）を設ける。
- クレジットカード等によるサブスクリプション課金（Stripe Billing 等の決済代行サービスを利用し、カード情報は自社で保持しない）。
- 支払い方法の登録・変更、請求履歴の閲覧、プランのアップグレード/ダウングレード/解約。
- 支払い失敗時の猶予期間・利用制限のルール（詳細は要確認 → §7）。

### 4.9 マーケティング・オンボーディング（商用化に伴う新規要件）
- 未ログインでも閲覧できるランディングページ（製品説明・料金表・サインアップ導線）。
- 初回ログイン後のオンボーディング（組織作成、最初のプロジェクト/カテゴリ登録の案内）。

## 5. 非機能要件

- **データ保存**: サーバー側のマネージドデータベース（PostgreSQL想定）に保存する。組織（テナント）単位でデータを論理分離する。
- **可用性**: オンライン前提（Webアプリのため）。将来的なオフライン対応（PWA）は §7 未決定。
- **軽量性・パフォーマンス**: 初期表示・タスク開始/切替操作は体感速度を重視し、レスポンスを軽量に保つ。
- **対応環境**: モダンブラウザ（Chrome/Edge/Safari/Firefoxの最新版目安）。レスポンシブ対応（PC優先、モバイルは閲覧・簡易操作を想定）。
- **技術スタック**: Next.js（App Router, TypeScript）+ PostgreSQL + Prisma ORM + Auth.js（認証）+ Stripe（課金）+ Tailwind CSS。詳細は [docs/GOVERNANCE.md](GOVERNANCE.md) §8、[docs/CICD.md](CICD.md) を参照。
- **ホスティング／インフラ**: AWSのサーバーレス最小構成（CloudFront+S3 / API Gateway+Lambda / Aurora Serverless v2。2026-07-24 /goal指示で決定）。詳細は [docs/AWS.md](AWS.md)。実デプロイは [docs/GOVERNANCE.md](GOVERNANCE.md) §6 に該当し管理者が実施する。
- **セキュリティ**: 決済情報（カード番号等）は自社で保持せず決済代行サービス（Stripe等）に委譲する。組織間データ分離を徹底し、認可漏れ（他組織データへのアクセス）を防ぐ。

## 6. データモデル（概念レベル・暫定）

- **User**: `id`, `email`, `name`, `password_hash`（またはOAuth連携情報）
- **Organization**: `id`, `name`, `plan`(`free` | `pro` 等), `stripe_customer_id`
- **Membership**: `id`, `user_id`, `organization_id`, `role`(`admin` | `member`)
- **Project/Category**: `id`, `organization_id`, `name`, `color`, `is_archived`
- **Task**: `id`, `organization_id`, `user_id`, `project_id`, `name`, `type`(`work` | `break`), `start_time`, `end_time`
- **Subscription**: `id`, `organization_id`, `stripe_subscription_id`, `status`, `current_period_end`
- **DailyLog（導出データ）**: 日別・プロジェクト別の集計はTaskから都度算出する想定（正規化データとして別テーブルを持つかは実装時に判断）。

各レコードに `created_at`/`updated_at` を持たせる。

## 7. 未決定事項・今後確認したい項目

以下は本要求定義の時点では未確定。実装着手前〜商用リリース前に管理者に確認する。

- カレンダー表示の集計単位（実働時間／タスク件数／両方切替可能か）
- 週表示・月表示以外（日表示・四半期表示など）の要否
- 工数データのエクスポート形式・外部システム（勤怠・会計等）連携の要否
- 長時間タスク未入力時のリマインド・通知機能の要否
- プロジェクト/カテゴリの「その場での新規登録」を許容するか、事前登録のみとするか
- 具体的なプラン数・価格・機能差分（Free/Proの境界線）
- 支払い失敗時の猶予期間・アカウント制限ルール
- OAuthログイン（Google等）の要否・優先度
- PWA化・オフライン対応の要否
- ~~ホスティングインフラの最終選定~~ → 2026-07-24決定: AWSサーバーレス構成（CloudFront+S3 / API Gateway+Lambda / Aurora Serverless v2、[docs/AWS.md](AWS.md)）。カスタムドメイン・DBマイグレーション方式等の残論点は同書§4-5参照
- 単体テストフレームワークの選定（暫定 Vitest を想定）、E2Eテスト（暫定 Playwright を想定）の要否
- 既存の非商用（ローカル保存・Windowsデスクトップアプリ）版の扱い（廃止するか、別ラインとして残すか）

## 8. スコープ外（現時点）

- 外部勤怠・工数管理システムとの自動連携
- 複数通貨・海外向け税務対応（初期は日本国内向けを想定）
- SSO/SAML等のエンタープライズ認証（将来検討）
