インストーラーの署名

hanamask の Windows インストーラー（.exe）にコード署名を施すために必要なものと、実施手順の調査結果。対象読者は管理者。

なぜ必要か

現在のインストーラーは未署名である（2026-08-08、PEヘッダの証明書テーブルが空であることを確認）。未署名の実行ファイルを配布すると、利用者の環境で次が起きる。

  • SmartScreen の警告: 「WindowsによってPCが保護されました」という青い画面が出る。「詳細情報」を押さないと実行できず、初めて触る人はここで止まる
  • ブラウザでのダウンロード時に警告が出ることがある
  • 一部のウイルス対策ソフトが未署名バイナリを疑わしいものとして扱う

必要なもの

1. コード署名証明書

2023年6月以降、Windows向けのコード署名証明書は秘密鍵をハードウェアに保管することが必須になった（CA/Browser Forum の要件変更）。以前のようにPFXファイルを買って終わり、という形は取れない。

種別保管方法SmartScreenへの効き方費用の目安（年）
OV（組織認証）USBトークン送付 or クラウドHSMすぐには消えない。評価が貯まるまで警告が出続ける3〜7万円
EV（拡張認証）USBトークン or クラウドHSM即座に消える6〜12万円

個人開発者の場合、OVでも取得できる事業者はあるが、法人より審査が長引きやすい（登記簿・電話確認などの代わりに、本人確認書類や第三者による事業実在性の確認が要る）。

2. 署名の実行環境

証明書の保管方法によって手順が変わる。

  • USBトークン: 物理的に挿した端末でしか署名できない。CIでの自動署名は困難
  • クラウドHSM（Azure Trusted Signing、DigiCert KeyLocker、SSL.com eSigner 等）: APIキーで署名でき、CIからも実行できる

Azure Trusted Signing は月額制（個人開発者向けの安価な区分がある）で、証明書の購入と管理を Microsoft 側に寄せられる。ただし利用資格の審査があり、組織の実在確認が要る。

設定方法

electron-builder.yml に署名設定を追加する。現在は署名関連の記述が一切ない。

win:
  # 証明書の指定方法は保管形態による
  certificateSubjectName: "組織名"        # 証明書ストア（トークン）から探す場合
  # または
  signtoolOptions:
    signingHashAlgorithms: ["sha256"]
    rfc3161TimeStampServer: "http://timestamp.digicert.com"

タイムスタンプの指定は必須。付けないと、証明書の有効期限が切れた瞬間に既存の配布物まで「無効な署名」として扱われる。

費用をかけない選択肢

証明書を取得しない場合でも、利用者の負担を減らす手はある。

  1. 配布ページで警告の回避手順を案内する（「詳細情報」→「実行」）。根本解決ではないが、初見の利用者が止まるのを防げる
  2. winget での配布: winget 経由のインストールは SmartScreen の経路を通らない。ただし公開リポジトリへの登録審査があり、未署名では通らない可能性が高い
  3. 署名せず配布し続ける: 個人利用・限定配布であれば実害は「毎回警告を押しのける手間」に留まる

判断が必要な点

  1. 配布の範囲。管理者本人と限られた相手だけなら、未署名のままでも実害は小さい。不特定多数へ配るなら署名は事実上必須
  2. 費用の許容度。年数万円の継続費用が発生する
  3. 法人か個人か。OV/EV とも組織の実在確認が前提で、個人名義では取得できない事業者もある
  4. CIでの自動署名が要るか。要るならクラウドHSM一択で、USBトークンは選べない

現状の確認方法

PEヘッダの証明書テーブルを直接見れば、外部ツール無しで判定できる。Windows 側からは Get-AuthenticodeSignature <path> でも確認できる。
