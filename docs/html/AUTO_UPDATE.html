自動更新

v2.2.0 から、hanamask は自分で新しい版を取ってきて入れ替わる。それまでは修正を配っても利用者が Releases から入れ直すしかなく、古いまま気付かれなかった（0.2.0 の「エージェントがノート本文を書き換えられない」不具合、2026-10 の HTTP2Shell 対応がその例）。

対象読者は管理者。仕組み・判断の経緯・リリース時の運用をまとめる。

1. 使っている道具

electron-updater（6.8.11、MIT）。直接依存は8件（semver / js-yaml / fs-extra / lazy-val / lodash.isequal / tiny-typed-emitter / lodash.escaperegexp / builder-util-runtime）。追加は 2026-10-25 に管理者が承認した（GOVERNANCE.html §6）。

配布側は electron-builder.yml の publish: github 宣言により、リリースのたびに latest.yml（更新の目印）と .blockmap（差分ダウンロード用）が作られ、release.yml が .exe と一緒に GitHub Releases へ添付する。アプリはこの latest.yml を読みに行く。リポジトリは公開済みなので、アクセストークンは要らない。

2. 動き方（2026-10-25 管理者決定）

項目決定
既定オン。設定画面の「更新を自動で確認する」で止められる。設定を開かない利用者にも修正を届けるため
確認の頻度起動の10秒後に1回、以降6時間ごと。準備ができた後は確認しない
ダウンロード新しい版があれば裏で自動
適用OS 通知と画面上部の帯で知らせ、「再起動して更新」か次回の終了時に入れ替わる。勝手に再起動しない
手動確認設定画面の「今すぐ確認」。自動確認を止めていても使える
失敗状態に「確認できませんでした」と出すだけ。オフラインでも普通に使える
動かない起動開発時（app.isPackaged が false）と E2E（HANAMASK_DB_PATH 指定時）

外部との通信はこの自動更新だけで、ノート・タスクの中身は送らない。公開サイト・README・SECURITY.md にも同じことを書いている。tests/main/no-network.test.ts は「mainプロセスは通信APIを持たない」ことに加え、electron-updater を読み込んでよいのは結線する src/main/index.ts だけであることを検査する。

ウィンドウを閉じても通知領域に残る設定（close-to-tray）では、ウィンドウを閉じる処理が終了を通知領域へ逃がしてしまう。「再起動して更新」は終了中の印（isQuitting）を先に立ててから quitAndInstall を呼ぶ。

実装: src/main/update/update-state.ts（イベントから状態を作る純粋関数）、src/main/update/auto-updater.ts（スケジュールと適用）、src/main/index.ts（結線とIPC）、src/renderer/components/UpdateSettings.tsx・UpdateBanner.tsx（画面）。

3. 未署名との組み合わせ（最重要）

インストーラーには署名を付けない判断をしている（SIGNING.md）。この状態で自動更新を入れるとどうなるかを、electron-updater の実装を読んで確かめた（2026-08-10）。2026-10-25、管理者はこの前提を受け入れて未署名のまま自動更新を入れると決めた。署名は別タスクで検討する。

署名の検証は、丸ごとスキップされる。

// NsisUpdater.js
async verifySignature(tempUpdateFile) {
  publisherName = (await this.configOnDisk.value).publisherName;
  if (publisherName == null) {
    return null;   // ← 検証せず「問題なし」として先へ進む
  }
  ...
}

publisherName は署名証明書から作られる値で、未署名のビルドでは存在しない。つまり「検証に失敗する」のではなく「検証されない」。

では何が守られているのか

守り未署名でも効くか
配信経路の暗号化（HTTPS）効く
latest.yml に書かれた sha512 との照合効く（DownloadedUpdateHelper が突き合わせる）
配布元が本人であることの証明（署名）効かない

latest.yml 自体も同じHTTPS経路で取ってくるので、その経路とGitHubを信頼することが前提になる。

判断材料

この信頼の形は、今の手動配布と同じである。利用者はいま、同じHTTPS経路で同じ場所から未署名の .exe を落として実行している。自動更新を入れても、信頼の前提は増えない。

変わるのは頻度と自動性で、一度信頼した経路が後から侵害された場合の影響が大きくなる（利用者が気付かないうちに置き換わる）。ここを重く見るなら、自動更新より先に署名を検討することになる。

4. リリースの運用

  • v2.1.1 以前の利用者には更新の仕組みが無い。自動更新入りの最初の版（v2.2.0）だけは手で入れ直してもらう。リリースノートに書く
  • 以降は今までどおりタグを打てば release.yml が latest.yml を添付し、利用中のアプリが拾う。latest.yml を添付し忘れると誰にも届かない（release.yml の添付ループが release/latest.yml を含むことを確認する）
  • 実際の更新経路は、リリース済みの版同士でしか確かめられない。v2.2.0 → v2.2.1（Electron 43.8.4 で同梱 Node を HTTP2Shell の修正版にする更新）を初回の実地確認とする: v2.2.0 を入れた PC で通知が出る → 「再起動して更新」で 2.2.1 になる → データがそのまま残る → ログで差分ダウンロード（blockmap）が使われたか見る
  • 更新を止めたい緊急時は、該当リリースを draft に戻すか latest.yml を外す（アプリは「最新です」のまま何もしない）
