# task-breakdown

`docs/REQUIREMENTS.md`（確定済み要求定義）を、Parallel Subagent Framework（`CLAUDE.md`）1本分＝概ね`SPEC.md` 1本分の粒度のタスクに分解し、`docs/TASKS.md`に一覧化する。要求定義の記述と実装単位は1対1にならないことが多い（1つの機能要件が複数タスクに分かれる、複数の要件が1タスクにまとまる）ため、機械的な見出し変換ではなく実装の依存関係・並列実行可否を踏まえて分割する。

## いつ使うか

- `docs/REQUIREMENTS.md`が初めて確定した、または大きく改訂されたとき（タスク一覧をゼロから、または差分で作り直す）。
- タスクが完了した、スコープが変わったとき（該当タスクのステータス・内容を更新する）。
- 実装を進める中で、当初想定していなかった作業単位が必要だと分かったとき（新規タスクを追記する）。

## タスク分割の考え方

1. `docs/REQUIREMENTS.md`を通読し、機能要件（§4系）・非機能要件（§5）・データモデル（§6）・ツール一覧（§7）を突き合わせる。
2. 1タスク＝1つの`SPEC.md`として後でPhase 1〜5フローに投入できる大きさに割る目安:
   - 新しいMCPツール群1〜数個＋対応するUI＋DB変更、が1タスクの標準的な大きさ（例: 「ノートの更新・ソフトデリート・復元」）。
   - 既存パターンの横展開（例: ノートで確立した仕組みをタスクに展開する）は1タスクにまとめてよい。
   - UIのみ・ドキュメントのみの変更は独立した小さいタスクにしてよい。
3. 依存関係を明示する（例: バージョニングは更新系ツールに依存、UI連携ツールはノート/タスク詳細画面に依存）。依存があるタスクは並列実行できないため、`docs/TASKS.md`の「依存」に前提タスクIDを書く。**必須**（前提タスクが無いと実装・テストが成立しない技術的依存）と**推奨**（無くても着手できるが、パターンの踏襲・内容の正確性のため後回しにした方が手戻りが少ないもの）を区別する。必須依存は**直接の前提タスクのみ**を書く（推移的に辿れる依存は書かない。例: T06がT03に依存し、T11がT06に依存するなら、T11の必須依存には「T06」とだけ書き「T03」は書かない — 波及は依存グラフを辿れば分かる）。
4. 既に実装済み・レビュー待ちの基盤/プロセスタスク（テスト方針整備、E2E基盤整備など）も「基盤・プロセス」セクションとして残す。要求定義から直接は導出されないが、開発を進める上での前提になっているため。
5. タスクを新設・変更したら、必須依存のみを辺とした依存グラフから着手可能な順（ウェーブ）を組み直し、`docs/TASKS.md`冒頭の「依存関係と着手順」表を更新する。同じウェーブのタスクは並列着手できる（直前のウェーブが全て完了してから次のウェーブに進む）。依存グラフの可視化（Mermaid図）は`docs/html/TASKS.html`側にのみ追加し、Markdown側には図を重複させない（`docs-html-sync` skillの運用に合わせる）。

## 各タスクに必須の項目

`docs/TASKS.md`の各タスクは以下を必ず埋める。空欄・「特になし」で済ませず、該当しない場合もその旨を明記する（禁止事項・停止条件が本当に無い場合のみ「特になし」でよい）。

| 項目 | 書き方 |
|---|---|
| 依存 | 必須依存（直接の前提タスクIDのみ）と推奨依存（無くても着手できるが後回しにした方が良い前提タスクID）を分けて書く。両方無いタスクは「必須: なし」（推奨も無ければ「／推奨: なし」も省略可）。 |
| 目的 | `docs/REQUIREMENTS.md`の該当節番号を引用しながら、このタスクが無いと何ができないかを1〜3文で書く。 |
| 変更範囲 | 触ってよい層・ディレクトリの見積もり（`src/main/db/`, `src/renderer/components/`等）。ファイル単位の確定は着手時の`SPEC.md` Part 2に委ねる。他タスクとの並列実行時に競合しそうな範囲が分かる粒度で書く。 |
| 禁止事項 | このタスクではやらないこと。次タスクの先取り・要求定義に無い機能の追加実装・スコープ外(`docs/REQUIREMENTS.md` §9)への越境を具体的に列挙する。 |
| テスト | `docs/TESTING.md`（単体テスト方針）・`.claude/skills/e2e-runner/SKILL.md`（GUI/E2E検証）を参照し、このタスクで最低限満たすべきテストの種類・シナリオを書く。「テストを書く」ではなく何を検証するかまで書く。 |
| 停止条件 | 管理者に確認せず自律的に進めてよい範囲の境界を書く。少なくとも以下は毎回チェックする: `docs/GOVERNANCE.md` §6（管理者承認が必要な操作。依存関係の大幅な追加、アーキテクチャ上の不可逆な決定等）に該当するか、`docs/REQUIREMENTS.md` §8（未決定事項）や要求定義に記載の無い仕様判断が必要か、CLAUDE.mdのセーフティ機構（自己修正3回超過）に触れる見込みがあるか。 |

## docs/TASKS.md の更新手順

1. `docs/REQUIREMENTS.md`と既存の`docs/TASKS.md`を読み、差分（新設すべきタスク、完了したタスク、スコープが変わったタスク）を洗い出す。
2. 新規タスクは末尾にタスクID（`T` + 連番）を採番して追記する。既存タスクIDは振り直さない（他ドキュメント・コミットメッセージからの参照が壊れるため）。
3. 完了したタスクは「ステータス」を`完了`にし、実装したPR番号・`SPEC.md`へのリンクを添える（`docs/TASKS.md`のT00〜T02を参照）。
4. タスクの新設・完了・依存関係の変更があれば、`docs/TASKS.md`冒頭の「依存関係と着手順」のウェーブ表を更新する。
5. `docs/TASKS.md`を編集したら、skill「docs-html-sync」に従い`docs/html/TASKS.html`を同期する（依存グラフのMermaid図は`docs/html/`側のみ）。
6. `docs/GOVERNANCE.md` §10のドキュメント一覧に`docs/TASKS.md`へのリンクが無ければ追加する。

## 絶対ルール

- 「依存」「禁止事項」「停止条件」を省略しない。特に依存・停止条件が無いタスクは意図的に「なし」「特になし」と明記し、書き漏れと区別できるようにする。
- タスクの完了報告を鵜呑みにせず、実際の差分・テスト結果を確認してから`docs/TASKS.md`のステータスを`完了`にする（`docs/GOVERNANCE.md` §5 レビュー運用に従う）。
