# feature-spec

Phase 1（調査）の結果を受け取り、リポジトリ直下（または対象機能のディレクトリ）に `SPEC.md` を生成する。この仕様書は Phase 3 以降、全サブエージェント共通の「正」になるため、曖昧さを残さないこと。

## 前提

- `docs/REQUIREMENTS.md` の機能要件・§7未決定事項と矛盾しないこと。矛盾する、または未決定事項に該当する場合は仕様書を書き進めず、その旨を明記して管理者に確認する。
- Phase 1 の調査結果（UI/データ取得/DB等の既存実装状況）を踏まえ、実在するコード・構造にのみ言及する。存在しないファイル・API を仮定しない。

## 出力形式（`SPEC.md`）

### Part 1: 利用者向け（管理者レビュー対象）

- 機能の説明（何を・なぜ）
- 画面イメージ・操作フロー（UI変更を伴う場合。スクリーンショットが必要な箇所には `📸` マークを付け、`e2e-runner` スキルで後から差し込めるようにする）
- 受け入れ条件（Acceptance Criteria）。ユーザーが動作を確認できる粒度で、チェックリスト形式にする。
- 未決定・要確認事項があれば明記する（`docs/REQUIREMENTS.md` §7 相当）。

Part 1 は簡潔・平易な日本語で書き、実装の内部事情（クラス名・関数名等）を持ち込まない。

### Part 2: AI用（レビュー不要・実装セット定義）

- **実装セット一覧**: タスクを、独立して並列実装できる単位（セット）に分解する。各セットに以下を明記する。
  - セット名
  - 目的（受け入れ条件のうちどれを満たすか）
  - 触ってよいファイル一覧（新規作成含む）
  - 依存する既存ファイル（読み取りのみ、編集しない）
  - 対応するテストの置き場所
- **並列グループ宣言**: どのセットとどのセットが同時実行可能か（ファイルが重複しない組）を明示する。共有ファイル（設定ファイル・ルーティング定義・DBスキーマ等）を複数セットが編集する必要がある場合は、そのセットを並列グループに含めず「Phase 4 統合ゲートでのみ編集」と明記する。
- **完了条件**: このSPECを満たしたとみなす機械判定可能な条件（例: 該当テストが全て緑、Lintが通る）。

## 生成後

- Part 1 のみを管理者に提示し、レビューを依頼する（停止①）。Part 2 は提示不要（AI向けのため）。
- 承認が得られるまで Phase 3（実装）のサブエージェントを起動しない。
- 承認後に修正が入った場合は `SPEC.md` を更新してから Phase 3 に進む。
